# uv override file for environments/requirements-semgrep.in ONLY.
# tools/update_dependencies.py passes it as `--overrides` for the `semgrep` spec.
#
# semgrep 1.166.0 through 1.178.0 (1.178.0 is pinned and was the latest on PyPI
# on 2026-09-30) declare `pyjwt[crypto]~=2.13.0`, so no available semgrep
# upgrade reaches a patched pyjwt, and a pyjwt floor in the .in makes the spec
# unsatisfiable. pyjwt 2.13.0 carries thirteen advisories, one critical, and 2.15.0
# is the first release that fixes all of them (2.14.0 left GHSA-42vr-xj54-vc7v
# open). This override replaces semgrep's and mcp's pyjwt requirement with the
# line below. The one alternative was a DOWNGRADE: semgrep 1.150.0 through
# 1.156.0 declare `pyjwt[crypto]~=2.4`, which admits 2.15.x (and 1.149.0 and
# earlier declare no pyjwt requirement of their own), but that is 22 minor
# versions (25 PyPI releases, 1.157.0 through 1.178.0) of the scanner backwards,
# and was rejected.
#
# Measured before adopting it, semgrep 1.177.0 on Linux / Python 3.11 against the
# same tree, with pyjwt 2.13.0 (the lock before this override) and 2.15.1 (the
# first lock compiled with it, installed from its committed blob):
#   - the blocking custom-rules scan returned 0 results and 0 errors over the same
#     189 files under both;
#   - the advisory `p/python` scan returned the same 3 SARIF results, all three
#     suppressed in source by `nosemgrep`, with the same 154 rules loaded;
#   - every `semgrep scan` IMPORTS pyjwt, because semgrep's CLI loads its `mcp`
#     command eagerly and that module imports jwt, so pyjwt's import-time
#     initialisation runs on every scan. After import, nothing calls it: a tracer
#     wrapping pyjwt's public functions, methods and module-level aliases logged 0
#     calls through both scans, custom-rules and advisory (each traced in the
#     semgrep entrypoint and its pysemgrep re-exec), under both versions, while
#     logging encode, decode and get_unverified_header in a control run under each.
#
# Re-measured 2026-09-30 for the semgrep 1.177.0 -> 1.178.0 bump, both locks
# carrying pyjwt 2.15.1, installed with CI's argv on Linux / Python 3.11 and
# scanned against the same tree: the blocking custom-rules scan returned 0
# results and 0 errors over 189 files under both, and the advisory scan the same
# 3 SARIF results, all suppressed by `nosemgrep`, with 154 rules loaded. 1.178.0
# declares exactly the requirements 1.177.0 does, pyjwt[crypto]~=2.13.0 included.
#
# CONSEQUENCES:
#   - The lock no longer satisfies semgrep's own metadata, so a resolving
#     `pip install -r environments/requirements-semgrep.txt` fails (measured: exit
#     1, and exit 0 with --no-deps). Every install of it must pass --no-deps, which
#     is safe because the lock is the complete hashed closure.
#   - Any recompile that does not pass this file walks pyjwt back to 2.13.0
#     (measured: `uv pip compile` without --overrides exits 0 with pyjwt 2.13.0).
#     Dependabot's pip-compile updater has no way to pass an override file, so its
#     grouped /environments PRs are expected to do the same.
#     tests/test_dependency_tooling.py fails such a lock, so a PR carrying one goes
#     red and has to be recompiled with tools/update_dependencies.py.
#   - The bound below stops at the measured minor series. Raising it means
#     re-running the scan comparison above against the new pyjwt first.
#
# EXIT CONDITION: once a semgrep release accepts pyjwt>=2.15.0, bump semgrep in
# the .in, delete this file and the spec's `overrides=` entry, drop --no-deps from
# security.yml's two semgrep installs, recompile and re-verify hashes.
pyjwt[crypto]>=2.15.0,<2.16
