# Hash-locked pip bootstrap. Installed first by the three Docker images (see
# Dockerfile), singularity.def and release.yml's pre-publish gate, and by every
# CI job that takes setuptools from a lock as a constraints file (the jobs
# installing requirements-ci.txt or requirements.lock), ahead of that setuptools
# install: taking hashes from a constraints file for an unpinned requirement
# arrived in pip 26.1 (24.0 and 25.0.1 refuse it, measured), and the pip a job
# starts with is not pinned.
#
# WHY THIS FILE EXISTS. pip never takes a hash as a flag on a bare `pip==X`
# spec, only from a requirements file (or, since 26.1, a constraints file, which
# the pip doing this install may predate), so the image's previous
# `pip install --user "pip==26.1.2"` step was version-pinned but not
# hash-pinned. Scorecard's PinnedDependencies check reads that as an unpinned
# pipCommand (`checks/raw/shell_download_validate.go`, isUnpinnedPipInstall:
# a bare package argument with no --require-hashes returns unpinned).
#
# WHY IT IS SEPARATE FROM requirements.lock. `--require-hashes` demands a hash
# for EVERY requirement in the file it is handed, and the bootstrap has to run
# BEFORE the production closure is installed. Keep this file to the single
# `pip` requirement; do not add anything else to it.
#
# Tier 4 in CONTRIBUTING.md's dependency-tier table: hand-maintained, no `.in`
# source. Regenerate with:
#   pip download pip==<version> --no-deps -d /tmp/pipboot                # wheel
#   pip download pip==<version> --no-deps --no-binary :all: -d /tmp/pipboot  # sdist
#   pip hash /tmp/pipboot/*
# Both the wheel and the sdist hash are listed so the install succeeds whether
# or not pip resolves to the wheel. Hashes below were cross-checked against the
# PyPI JSON API, the PEP 691 simple index, and a local sha256 of the downloaded
# bytes on 2026-09-07.
#
# WHY 26.2.1 AND NOT 26.1.2. Writing the bootstrap as a manifest is what first
# made this pin visible to the dependency-review action, which scans manifest
# files and never reads a RUN line. It immediately reported GHSA-qwm4-qh6w-59xr
# (moderate, "pip would incorrectly handle doubly-encoded package URLs from
# indexes"), first patched in 26.2.0. The image was ALREADY installing the
# affected 26.1.2 before this file existed; the manifest did not introduce the
# exposure, it revealed it. Keep this pin at or above 26.2.0.
pip==26.2.2 \
    --hash=sha256:3a8e5c800492787f33a4114ef54444546c340df428974ebba17e0fd47e11af2f \
    --hash=sha256:fd7f4dfa8190e014013b9f08f3e973f4e4c26ffd179a204895533a7254813a70
